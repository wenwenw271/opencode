# 会话待办列表

本文档说明 opencode 中会话待办列表（Todo）如何产生、由谁写入与读取，以及是否存在用户手动调用 todoread/todowrite 的实现。

---

## 1. 结论概览

- **产生方式**：待办列表由**主 Agent（LLM）在对话中主动调用 todowrite 工具**产生并更新；没有“用户直接创建/编辑待办”的独立入口。
- **持久化**：todowrite 执行时调用 `Todo.update({ sessionID, todos })`，先删除该会话下所有 todo 行，再插入本次传入的整份列表（见 `session/todo.ts`）。
- **读取**：Agent 可通过 **todoread** 工具读取当前列表；TUI 与 HTTP API 通过 `Todo.get(sessionID)` 或订阅 `todo.updated` 展示，**不**通过“调用 toread 工具”实现。
- **手动调用工具**：**没有**用户手动触发 todowrite 或 toread **工具**的实现；仅存在“通过 HTTP GET 直接读待办”的接口，无“用户手动写待办”的 API 或 UI。

---

## 2. 待办列表如何产生

### 2.1 写入路径唯一：todowrite 工具 → Todo.update

- 数据库 **todo** 表仅在一处被写入：`Todo.update({ sessionID, todos })`（`session/todo.ts`）。
- `Todo.update` 仅被 **TodoWriteTool（todowrite）** 的 `execute` 调用（`tool/todo.ts`）。
- 因此：**只有主 Agent 在本轮中调用了 todowrite 工具并成功执行时，才会更新或产生该会话的待办列表。**

流程简述：

1. 用户在当前会话发消息（如多步任务请求）。
2. 主 Agent 拥有 todowrite 工具，并根据 **todowrite.txt** 的说明判断“需要任务列表”（多步、非平凡、用户给多任务等）。
3. Agent 发起工具调用：`todowrite({ todos: [ { content, status, priority }, ... ] })`。
4. **TodoWriteTool.execute** 先请求 todowrite 权限（`ctx.ask`），通过后执行 `Todo.update({ sessionID: ctx.sessionID, todos: params.todos })`。
5. **Todo.update**：对该 `session_id` 先 `delete` 所有行，再 `insert` 本次 `todos`（带 position 0,1,2…），即**整表替换**该会话的待办。

### 2.2 初始状态与内容来源

- 新建会话时**不会**自动插入任何 todo；**Todo.get(sessionID)** 在从未写入前返回 `[]`。
- 列表第一次出现，即主 Agent **第一次成功调用 todowrite** 之后。
- 具体条目（content、status、priority）**全部由 LLM 根据当前对话和 todowrite.txt 的规则生成**；用户不直接编辑 todo 表。

### 2.3 子会话无待办

- 子 agent 会话创建时会将 **todowrite / todoread** 关闭（`task.ts` 中 `tools: { todowrite: false, todoread: false, ... }`）。
- 子 agent 既不能写也不能读待办；**会话待办仅存在于主会话**，由主 Agent 通过 todowrite 维护。

---

## 3. 待办的读取方式

| 方式 | 实现 | 说明 |
|------|------|------|
| **Agent 读** | toread 工具 → `Todo.get(ctx.sessionID)` | Agent 调用 toread 获取当前列表；todoread 在 registry 中默认被注释，非所有环境都暴露。 |
| **TUI 展示** | 同步层拉取 + 事件 | 初始加载时 `sdk.client.session.todo({ sessionID })`（即 GET API）；之后订阅 `todo.updated` 更新 store；侧栏从 `sync.data.todo[sessionID]` 读并展示。 |
| **HTTP API 读** | GET `/:sessionID/todo` | 直接调用 `Todo.get(sessionID)` 返回 JSON，**不**经过 toread 工具。 |

---

## 4. 是否存在手动调用 todoread / todowrite 的实现

### 4.1 todoread（读待办）

- **作为“工具”被用户手动触发**：**无**。没有 UI 按钮或命令让用户“现在执行一次 toread 工具”。
- **“手动读待办”的等价实现**：
  - **HTTP**：GET `/session/:sessionID/todo` 直接调用 `Todo.get(sessionID)` 返回列表（`server/routes/session.ts`）。客户端可据此实现“用户点击刷新待办”等，但这是**直接读库**，不是调用 toread 工具。
  - **TUI**：侧栏待办来自 sync store，数据来源为上述 GET 与 `todo.updated` 事件，同样**不**经过 toread 工具。

因此：**没有“用户手动调用 toread 工具”的实现**；有“通过 API 或 TUI 间接读待办”的能力。

### 4.2 todowrite（写待办）

- **作为“工具”被用户手动触发**：**无**。没有 UI 或 API 让用户提交一份 `todos` 并“执行一次 todowrite 工具”。
- **写待办的唯一路径**：主 Agent 在对话中调用 todowrite → `TodoWriteTool.execute` → `Todo.update`。
- **HTTP**：仅有 GET todo，**没有** POST/PUT 等“更新待办”的接口，即**没有**直接调用 `Todo.update` 的 API。
- **TUI**：有 **TodoWrite** 组件，用于**渲染**某条消息中“agent 调用了 todowrite”的 tool part（展示当时写入的列表），**不是**让用户编辑列表并触发 todowrite 的入口。

因此：**没有用户手动调用 todowrite 的实现**；也没有不经过工具、由用户直接写待办的 API 或 UI。

### 4.3 小结表

| 能力 | 是否实现 | 说明 |
|------|----------|------|
| 用户手动调用 **todoread 工具** | 否 | 无对应 UI/命令/API。 |
| 用户/客户端**读**待办（等价能力） | 是 | GET `/:sessionID/todo` 直接 `Todo.get()`；TUI 侧栏展示同一数据。 |
| 用户手动调用 **todowrite 工具** | 否 | 无对应 UI/命令/API。 |
| 用户/客户端**写**待办（等价能力） | 否 | 无 POST/PUT todo 的 API，无“用户编辑待办并保存”的 UI。 |

---

## 5. 相关代码位置

- **Todo 读写**：`session/todo.ts`（`Todo.update`、`Todo.get`，事件 `todo.updated`）。
- **工具定义**：`tool/todo.ts`（TodoWriteTool、TodoReadTool）。
- **工具描述**：`tool/todowrite.txt`（何时用/不用、状态与顺序约定）。
- **子会话禁用**：`tool/task.ts`（子会话 `tools: { todowrite: false, todoread: false }`）。
- **HTTP 读待办**：`server/routes/session.ts`（GET `/:sessionID/todo` → `Todo.get(sessionID)`）。
- **TUI 展示**：`cli/cmd/tui/context/sync.tsx`（todo 存储、`todo.updated`、初始 `session.todo` 拉取）；`cli/cmd/tui/routes/session/sidebar.tsx`（侧栏待办列表）；`cli/cmd/tui/routes/session/index.tsx`（TodoWrite 渲染 tool part）。
