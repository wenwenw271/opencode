# 死循环的避免与处理

本文档说明 opencode 如何避免和打断「LLM 反复以相同方式调用工具」导致的死循环，以及权限拒绝、上下文溢出、异常重试等如何参与循环的终止；并补充**除工具死循环外**其他可能的长循环/风险场景。

---

## 1. 结论概览

- **工具调用死循环**：通过 **doom_loop 权限** 检测「同一工具 + 同一参数」连续调用达到阈值（默认 3 次）时，**先询问用户**（allow 才继续执行该次调用）；用户拒绝则抛出 `RejectedError`，process 返回 `"stop"`，loop 结束。
- **权限/Question 拒绝**：某次工具执行被用户拒绝（`PermissionNext.RejectedError` / `Question.RejectedError`）时，若未开启 `continue_loop_on_deny`，则置 `blocked = true`，本轮结束后 process 返回 `"stop"`，loop 结束。
- **上下文溢出**：每步结束（finish-step）或捕获到 `ContextOverflowError` 时置 `needsCompaction = true`，跳出流处理并返回 `"compact"`，由 loop 触发压缩或报错，从而避免在超长上下文中继续循环。
- **异常与重试**：可重试错误（如部分 API 错误）会按 `SessionRetry` 延迟后 `continue` 重试；不可重试或重试后仍失败则写 error 并置 idle，loop 通过 `assistantMessage.error` 等结束。

opencode **没有**硬性「最大轮数」限制，终止依赖上述机制与用户/配置行为。

---

## 2. doom_loop：同工具同参数连续调用

### 2.1 触发条件

在 **SessionProcessor** 消费 `fullStream` 时，当收到 **tool-call**（工具名与参数就绪）事件时：

- 取当前助手消息的 **parts** 中**最近 N 条**（`N = DOOM_LOOP_THRESHOLD`，默认 **3**）。
- 若这 N 条**都是**同一工具、同一参数（`JSON.stringify(p.state.input) === JSON.stringify(value.input)`），且都不是 `pending`，则视为「重复调用」，**在执行该工具前**先请求 **doom_loop** 权限。

代码位置：`packages/opencode/src/session/processor.ts`（`case "tool-call"` 分支内，约 191–214 行）。

```ts
const DOOM_LOOP_THRESHOLD = 3
// ...
const lastThree = parts.slice(-DOOM_LOOP_THRESHOLD)
if (
  lastThree.length === DOOM_LOOP_THRESHOLD &&
  lastThree.every(
    (p) =>
      p.type === "tool" &&
      p.tool === value.toolName &&
      p.state.status !== "pending" &&
      JSON.stringify(p.state.input) === JSON.stringify(value.input),
  )
) {
  await PermissionNext.ask({
    permission: "doom_loop",
    patterns: [value.toolName],
    ...
  })
}
```

### 2.2 用户选择与结果

- **允许（once / always）**：`PermissionNext.ask` resolve，该次工具调用继续由 SDK 执行，loop 照常。
- **拒绝（reject）**：`PermissionNext.ask` 内会 `reject(RejectedError)`，异常从 process 的 `for await` 中抛出，被外层 catch 捕获；若该错误不可重试，则写入 `assistantMessage.error`，process 末尾判断 `input.assistantMessage.error` 后返回 `"stop"`，**loop 结束**。

因此：**死循环的「避免」** = 第 3 次相同调用时先问用户；**「解决」** = 用户拒绝后不再执行该次调用并结束会话轮次。

### 2.3 配置与权限

- **Agent 默认权限**（`agent/agent.ts`）：`doom_loop: "ask"`，即默认需要询问。
- **配置**：可在项目/全局 permission 中覆盖 `doom_loop`（如改为 `allow` 则不再询问，风险自负）。
- **TUI 提示**：`tips.tsx` 中说明 “Permission doom_loop prevents infinite tool call loops”；权限弹窗（`permission.tsx`）对 `doom_loop` 有专门文案（如 “Continue after repeated failures”）。

## 3. 权限/Question 拒绝与 blocked

- 当某次**工具执行**失败且错误为 `PermissionNext.RejectedError` 或 `Question.RejectedError` 时（`case "tool-error"`），会置：

  `blocked = shouldBreak`

  其中 `shouldBreak = (config.experimental?.continue_loop_on_deny !== true)`，即**未**开启「拒绝后继续 loop」时，`blocked === true`。

- process 在流处理与收尾完成后，若 `blocked === true`，则 **return "stop"**，loop 不再继续下一轮。

因此：**用户在任何一次权限/Question 上选拒绝，且未开 continue_loop_on_deny 时，会终止本轮 loop**，避免在用户已拒绝的情况下继续尝试同类操作。

---

## 4. 上下文溢出与 needsCompaction

- **finish-step**：每步（含 token 使用量）结束时调用 `SessionCompaction.isOverflow({ tokens, model })`；若为 true，则置 `needsCompaction = true`，随后在 `for await` 中 `if (needsCompaction) break` 跳出流消费。
- **捕获到 ContextOverflowError**：在 process 的 catch 中若 `MessageV2.ContextOverflowError.isInstance(error)`，同样置 `needsCompaction = true` 并发 `Session.Event.Error`。
- process 收尾时若 `needsCompaction === true`，则 **return "compact"**；loop 侧会触发压缩流程（或报错），从而**避免在超长上下文中继续跑 LLM**，间接避免「因上下文爆掉而反复重试」的无效循环。

---

## 5. 异常与重试（SessionRetry）

- process 的 **catch** 中：
  - 若为 **ContextOverflowError**：只设 `needsCompaction`，不重试。
  - 否则调用 **SessionRetry.retryable(error)**：
    - 若返回**可重试**：`attempt++`，按 `SessionRetry.delay()` 等待后 **continue** 再次进入 `while (true)`，实现有限次重试。
    - 若**不可重试**（或未配置重试）：将 error 写入 `input.assistantMessage.error`，置 status 为 idle；process 末尾 **return "stop"**，loop 结束。

因此：**可重试错误**（如部分 5xx、限流）会延迟后重试；**不可重试错误**或**用户拒绝类错误**会直接结束 loop，避免无限重试。

---

## 6. 流程小结

| 机制 | 触发条件 | 行为 |
|------|----------|------|
| **doom_loop** | 同一工具、同一参数连续调用 ≥ 3 次 | 执行前请求 doom_loop 权限；用户拒绝则抛错 → process 返回 "stop"，loop 结束。 |
| **blocked** | 某次工具执行失败且为 RejectedError，且未开 continue_loop_on_deny | process 返回 "stop"，loop 结束。 |
| **needsCompaction** | finish-step 时 isOverflow，或捕获 ContextOverflowError | 跳出流处理，process 返回 "compact"；loop 做压缩或报错，不再继续正常轮次。 |
| **assistantMessage.error** | 不可重试异常或 doom_loop 等拒绝后抛错 | process 返回 "stop"，loop 结束。 |
| **SessionRetry** | 可重试错误（如部分 APIError） | 延迟后 continue 重试，有上限与退避，避免无限重试。 |

## 7. 其他可能的长循环/风险场景

除「同一工具 + 同一参数」连续调用（由 doom_loop 兜底）外，以下场景也可能导致**长时间或反复循环**，需结合上下文溢出、用户中止或配置来终止。

### 7.1 不同工具或不同参数的反复调用

- **现象**：LLM 一直发起工具调用，但每次工具或参数不同（如 A → B → A → B，或 read(file1) → read(file2) → grep(...)），**不会**触发 doom_loop（doom_loop 只检测「同工具 + 同参数」连续 3 次）。
- **当前行为**：process 的 `while (true)` **没有**最大轮数或「调用模式」检测，会一直执行直到：
  - 模型某轮不再发 tool-call、返回 stop；或
  - 上下文溢出 → needsCompaction → 压缩或报错；或
  - 用户中止（abort）；或
  - 某次工具执行触发权限/Question 拒绝且未开 continue_loop_on_deny（blocked）。
- **结论**：存在「变种工具循环」理论风险，依赖上下文上限或用户干预终止；若希望硬性上限，可给 agent 配置 `steps`（见下）。

### 7.2 压缩反复触发（compact → continue → 再次溢出）

- **现象**：overflow → process 返回 `"compact"` → loop 执行压缩后 `continue` → 下一轮 again 上下文超限 → 再次 compact。
- **当前行为**：压缩逻辑中，若**压缩后仍超限**（如会话过大无法再压），会设置 `ContextOverflowError` 并 **return "stop"**，loop 结束，不会无限压缩。但可能出现多轮「compact → continue → overflow → compact」直到失败或成功压到可继续。
- **结论**：有自然上界（压缩失败即 stop），不是严格死循环，但可能多轮压缩。

### 7.3 agent.steps 的软限制

- **配置**：Agent 可配置 `steps: N`（正整数），loop 中 `maxSteps = agent.steps ?? Infinity`，`isLastStep = step >= maxSteps`。
- **行为**：当 `isLastStep === true` 时，会在发给模型的 messages 末尾**注入一条「助手」消息**，内容为 `MAX_STEPS` 文案（“CRITICAL - MAXIMUM STEPS REACHED... Do NOT make any tool calls. Respond with text only”），**工具列表仍会传给模型**，并未在 API 层禁用工具。
- **结论**：这是**提示级软约束**，若模型遵守则通常会以纯文本收尾并结束；若模型仍发 tool-call，仍会执行，且下一轮仍为 isLastStep，可能形成「一直提示别用工具却仍被调用」的循环，直到 doom_loop、溢出或用户中止。

### 7.4 用户中止（abort）

- **行为**：loop 每轮开头有 `if (abort.aborted) break`；process 内部流式消费时也会 `input.abort.throwIfAborted()`。用户取消会话会触发 abort，从而**随时**终止循环。
- **结论**：任何长循环或死循环场景下，用户均可通过中止会话退出。
