# 流式处理与完整消息拼接

本文档说明 opencode 在 process 内如何流式消费 LLM 输出、如何在内存中拼接完整内容、如何落库，以及 `SessionPrompt.prompt()` 为何能返回完整的一条助手消息。

---

## 1. 结论概览

- **`SessionPrompt.prompt()`** 返回的是**完整的一条助手消息**（`MessageV2.WithParts`），不是流式数据块。
- **完整内容的拼接**在 **SessionProcessor** 内完成：流式阶段在**内存**里按块累加（如 `currentText.text += value.text`），在**文本块结束（text-end）**时用 `Session.updatePart(currentText)` 把整段 part 写入 DB。
- **`Session.updatePartDelta`** 只发布 `message.part.delta` 事件，**不写 DB**；用于 TUI/ACP 前端做流式打屏，与「完整消息落库」无关。
- **loop 返回时**通过 `MessageV2.stream(sessionID)` 从 DB 读取消息，此时各 part 已在对应「块结束」时以完整内容写入，故读到的是完整助手消息。

---

## 2. 调用链

```
SessionPrompt.prompt(input)
  → createUserMessage(input)
  → loop({ sessionID })
      → 每轮: processor.process(streamInput)
              → LLM.stream(streamInput)
              → for await (const value of stream.fullStream)  // 流式消费
                    text-start  → updatePart(空 text part)
                    text-delta  → currentText.text += value.text; updatePartDelta(delta)  // 仅发事件
                    text-end    → updatePart(currentText)   // 完整 text 写 DB
                    tool-call / reasoning 同理
      → break 后: for await (const item of MessageV2.stream(sessionID))
                    return item  // 第一条 assistant 即最新一条，从 DB 读出，已完整
  → 返回该条完整助手消息
```

---

## 3. Processor 内的流式消费与拼接

### 3.1 文本块（text）

- **text-start**：创建 `currentText = { type: 'text', text: '', ... }`，`Session.updatePart(currentText)` 写入 DB（此时 `text` 为空）。
- **text-delta**（每个流式块）：
  - **内存**：`currentText.text += value.text`，在进程内把整段内容拼完整。
  - **持久化**：不在此处改 DB 中的 part 内容，只调 `Session.updatePartDelta({ partID, field: "text", delta: value.text })` 发事件。
- **text-end**：
  - 对 `currentText.text` 做 trim、插件等处理。
  - `Session.updatePart(currentText)` 再写一次 DB，此时 `currentText.text` 已是**完整文本**，DB 中该 part 的 `data.text` 即完整内容。

代码位置：`packages/opencode/src/session/processor.ts`（`case "text-delta"`、`case "text-end"`）。

### 3.2 推理块（reasoning）

逻辑与文本块类似：`reasoning-delta` 时 `part.text += value.text` 并在内存中累积，同时 `updatePartDelta` 发事件；块结束时通过 `updatePart` 将完整 reasoning part 写入 DB。

### 3.3 工具调用（tool）

工具调用 part 在流式阶段创建/更新（tool-call-start、tool-call-delta 等），在工具执行完成后用 `Session.updatePart(part)` 写入完整 state（input、output、status 等）。不依赖「逐 delta 拼 text」的模式，但同样是**在合适的时机一次性写入完整 part**。

---

## 4. updatePart 与 updatePartDelta 的区别

| 方法 | 作用 | 是否写 DB |
|------|------|-----------|
| **Session.updatePart(part)** | 插入或更新整条 part（含完整 `data`，如 type、text、state） | ✅ 是；`PartTable` 的 `data` 被整条写入/覆盖 |
| **Session.updatePartDelta(input)** | 发布 `MessageV2.Event.PartDelta`（`message.part.delta`） | ❌ 否；仅发事件 |

代码位置：

- `packages/opencode/src/session/index.ts`：`updatePart` 写 `PartTable`，`updatePartDelta` 仅 `Bus.publish(MessageV2.Event.PartDelta, input)`。
- TUI：`packages/opencode/src/cli/cmd/tui/context/sync.tsx` 中订阅 `message.part.delta`，在内存 store 里对 `part[field] += delta`，用于流式打屏。

因此：**完整内容的持久化只由 `updatePart` 在「块结束」时完成；delta 只驱动前端实时显示。**

---

## 5. loop 的返回与完整消息的来源

loop 在 `result === "stop"`（或压缩等）后退出 while，然后执行：

```ts
for await (const item of MessageV2.stream(sessionID)) {
  if (item.info.role === "user") continue
  const queued = state()[sessionID]?.callbacks ?? []
  for (const q of queued) q.resolve(item)
  return item
}
```

- `MessageV2.stream(sessionID)` 按时间**倒序**（新→旧）从 DB 拉取消息。
- 第一个 `role === "assistant"` 的 `item` 即为**当前会话最新一条助手消息**。
- 该消息及其 `parts` 均从 **DB** 读取；各 part 已在各自的 text-end / reasoning-end / tool 完成时通过 `updatePart` 以完整内容写入，因此 **item 即完整的一条助手消息**。

故 `SessionPrompt.prompt()` 的返回值 = loop 的返回值 = 从 DB 读出的、已拼好的最新一条 assistant 消息。

---

## 6. 小结表

| 环节 | 行为 |
|------|------|
| 流式中（text-delta / reasoning-delta） | Processor 内 `part.text += value.text` 在内存中拼完整串；`updatePartDelta` 仅发事件供前端流式显示；**不按 delta 写 DB**。 |
| 块结束（text-end / reasoning-end / tool 完成） | `Session.updatePart(part)` 将内存中已完整的 part 写入/更新到 DB。 |
| 前端流式显示 | 订阅 `message.part.delta`，在内存 store 中 `part[field] += delta` 实现打字机效果。 |
| prompt() 返回 | loop 结束后从 DB 通过 `MessageV2.stream(sessionID)` 取最新 assistant 消息；内容已在 process 中拼好并落库，故为完整消息。 |
