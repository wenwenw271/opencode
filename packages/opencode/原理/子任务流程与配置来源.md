# 子任务流程与配置来源

本文档整理两方面的说明：

1. **子任务全流程**：子任务如何创建、执行与结束（含 SubtaskPart、TaskTool、loop、cancel）。
2. **配置来源**：`agent.mode === "subagent"` 与 `command.subtask === true` 从哪里来、是否在界面可配。

---

## 一、子任务全流程

### 1.1 概念与数据结构

- **子任务**在实现上对应两类东西：
  - **SubtaskPart**：用户消息里的一个 part，`type: "subtask"`，描述「要由子代理执行的一件任务」。
  - **子会话 (Session)**：执行该任务时创建的会话，`parentID = 主会话 ID`，在子会话里跑一轮 `SessionPrompt.prompt`（即一次 loop）。

- **SubtaskPart 结构**（`session/message-v2.ts`）：

```ts
export const SubtaskPart = PartBase.extend({
  type: z.literal("subtask"),
  prompt: z.string(),
  description: z.string(),
  agent: z.string(),
  model: z.object({ providerID: z.string(), modelID: z.string() }).optional(),
  command: z.string().optional(),
})
```

---

### 1.2 创建：子任务从哪里来

#### 入口一：命令 / 子代理执行

当执行**命令**且该命令被配置为「以子任务方式跑」时，会构造一条**只带 SubtaskPart 的用户消息**，再进入主会话的 prompt/loop。

**位置**：`session/prompt.ts` 的 `executeCommand` 内。

```ts
// 子代理或命令标记为 subtask 时，发一条 subtask part 由 loop 中 TaskTool 执行
const isSubtask =
  (agent.mode === "subagent" && command.subtask !== false) || command.subtask === true
const parts = isSubtask
  ? [{
      type: "subtask" as const,
      agent: agent.name,
      description: command.description ?? "",
      command: input.command,
      model: { providerID: taskModel.providerID, modelID: taskModel.modelID },
      prompt: templateParts.find((y) => y.type === "text")?.text ?? "",
    }]
  : [...templateParts, ...(input.parts ?? [])]

const result = await prompt({ sessionID, messageID, model: userModel, agent: userAgent, parts, ... })
```

- **何时是子任务**：`command.subtask === true`，或 agent 为 subagent 且 `command.subtask !== false`。
- **结果**：`parts` 里只有一个 `type: "subtask"` 的 part，然后调用 `prompt()`，进入主会话的 loop。

#### 入口二：用户消息持久化

`prompt()` 会先创建用户消息再进入 loop：

```ts
const message = await createUserMessage(input)
return loop({ sessionID: input.sessionID })
```

在 `createUserMessage` 里，对 `input.parts` 中**非 file、非 agent** 的 part（包含 subtask）走默认分支，原样带上 `messageID`/`sessionID` 写入，最后通过 `Session.updateMessage(info)` 和 `Session.updatePart(part)` 持久化。因此：**子任务在存储层的创建** = 一条用户消息 + 其中 type 为 `"subtask"` 的 part 被持久化。

#### 另一种「子任务」：LLM 调用 Task 工具

主会话 loop 里，模型可以调用 **Task 工具**。Task 工具内部会**创建子会话**并在子会话里跑一次 prompt；这是子任务**执行侧**的创建（子会话 + 一次子会话的 loop）。**SubtaskPart** 仍只来自：命令入口，或用户/前端直接发带 subtask 的 parts。

---

### 1.3 执行：loop 如何消费 SubtaskPart

#### 收集未处理的 compaction / subtask

`SessionPrompt.loop` 从当前会话消息流里，从后往前找 lastUser、lastAssistant、lastFinished，并收集所有**尚未被「完成掉的」** compaction / subtask part 到 `tasks`，然后 `task = tasks.pop()` 取一个。

```ts
let tasks: (MessageV2.CompactionPart | MessageV2.SubtaskPart)[] = []
for (let i = msgs.length - 1; i >= 0; i--) {
  const msg = msgs[i]
  // ... 找 lastUser, lastAssistant, lastFinished
  const task = msg.parts.filter((part) => part.type === "compaction" || part.type === "subtask")
  if (task && !lastFinished) tasks.push(...task)
}
const task = tasks.pop()
```

#### 若是 subtask：造助手消息 + Tool Part，再调 TaskTool.execute

当 `task?.type === "subtask"` 时，loop 不调 LLM，而是：

1. 创建一条**助手消息**（模拟「模型决定调用 Task 工具」）。
2. 创建一条 **tool part**（`tool: TaskTool.id`，`state.input` 里带 `prompt, description, subagent_type, command`）。
3. 调用 **TaskTool.execute**，传入这些参数。

#### TaskTool.execute：创建子会话并在子会话里跑 prompt

`tool/task.ts` 中：

- **创建或复用子会话**：有 `task_id` 则复用，否则 `Session.create({ parentID: ctx.sessionID, title: ..., permission: ... })`。
- **在子会话里执行**：`SessionPrompt.prompt({ sessionID: session.id, agent, tools: { todowrite: false, todoread: false, ... }, parts: promptParts })`，即子会话跑一整轮 loop，得到结果。
- **返回**：把子会话最后一条助手消息中的文本包成 `<task_result>...</task_result>` 作为 `output` 返回给主会话。

#### loop 写回结果并决定是否继续

执行完 `taskTool.execute` 后，loop 会：

- 把对应 tool part 的 state 更新为 `completed`（带 output）或 `error`。
- 更新该助手消息的 `finish`。
- 若该 subtask 来自命令（`task.command` 存在），会插入一条 synthetic user 消息：「Summarize the task tool output above and continue with your task.」，然后 `continue` 进入下一轮 loop，让主会话的模型继续总结并回复。

### 1.4 结束与取消（「销毁」）

opencode 里**没有在子任务结束时删除子会话或删除 SubtaskPart**；所谓「销毁」主要体现在：**结束 loop、取消状态、以及主/子会话的取消联动**。

#### 单会话 loop 退出时：cancel(sessionID)

每个会话的 loop 在进入时用 `defer` 注册「退出时取消该会话」：

```ts
using _ = defer(() => cancel(sessionID))
```

`cancel` 的实现（`session/prompt.ts`）：

```ts
export function cancel(sessionID: string) {
  const s = state()
  const match = s[sessionID]
  if (!match) {
    SessionStatus.set(sessionID, { type: "idle" })
    return
  }
  match.abort.abort()
  delete s[sessionID]
  SessionStatus.set(sessionID, { type: "idle" })
}
```

即：abort 该会话的 AbortController、从 state 移除、会话状态设为 idle。子会话的 loop 在 `SessionPrompt.prompt` 返回后同样会因 defer 触发 `cancel(session.id)`。

#### 主会话被取消时，子会话一起取消

TaskTool 在子会话上挂了主会话的 abort 监听：

```ts
function cancel() {
  SessionPrompt.cancel(session.id)
}
ctx.abort.addEventListener("abort", cancel)
using _ = defer(() => ctx.abort.removeEventListener("abort", cancel))
```

主会话被取消（例如用户点击停止）时，会顺带取消子会话的 loop。会话和消息数据仍保留在 DB，只是不再有活跃 loop。

### 1.5 流程串联小结

| 阶段   | 行为 | 主要位置 |
|--------|------|----------|
| **创建** | 命令/子代理入口根据 `command.subtask` 或 agent 模式构造 `parts: [SubtaskPart]`，再 `prompt()` → `createUserMessage()` → `Session.updateMessage` + `Session.updatePart` 写入带 subtask 的用户消息。 | `prompt.ts`: `executeCommand`、`createUserMessage` |
| **执行** | loop 收集未处理的 compaction/subtask，若当前为 subtask：创建助手消息 + Task tool part，调用 `TaskTool.execute`；Task 内部 `Session.create(parentID)` 创建子会话，`SessionPrompt.prompt(session.id, ...)` 在子会话跑一轮，结果以 `<task_result>` 返回；loop 把 tool part 标成 completed/error，可选插入 synthetic user 并 `continue`。 | `prompt.ts`: `loop`；`task.ts`: `Session.create`、`SessionPrompt.prompt`、返回值 |
| **结束** | 子会话 loop 正常结束或主会话 abort 时调用 `SessionPrompt.cancel(sessionID)`：abort、删 state、置 idle；会话与消息不删，仅不再有活跃 loop。 | `prompt.ts`: `cancel`；`task.ts`: `ctx.abort` → `SessionPrompt.cancel(session.id)` |

## 二、agent.mode 与 command.subtask 的配置来源

### 2.1 结论概览

- **agent.mode** 与 **command.subtask** 均**不在使用界面（聊天 UI）里配置**。
- 它们来自：**opencode 内置默认（代码写死）** + **配置文件 / 项目内 Markdown 的 frontmatter**。

| 项目            | 是否「自动」 | 实际来源 | 界面上是否有 |
|-----------------|--------------|----------|----------------|
| **agent.mode**  | 部分是       | 内置默认 + `opencode.json` 的 `agent.<name>.mode` + `.opencode/agents/<name>.md` 的 frontmatter | **没有** |
| **command.subtask** | 部分是   | 内置默认 + `opencode.json` 的 `command.<name>.subtask` + `.opencode/command(s)/<name>.md` 的 frontmatter | **没有** |

---

### 2.2 agent.mode === "subagent"

#### 内置默认（代码写死）

在 `agent/agent.ts` 里，每个内置 agent 的 `mode` 是写死的：

- **primary**：`build`、`plan`、`compaction`、`title`、`summary`。
- **subagent**：`general`、`explore`。

因此 **general / explore 默认就是 subagent**，无需任何配置。

#### 用户覆盖方式（仅配置，无 UI）

- **JSON 配置**：在 `opencode.json` 或 `~/.config/opencode/opencode.json` 中通过 `agent.<名字>.mode` 覆盖，例如：

  ```json
  {
    "agent": {
      "general": { "mode": "subagent" },
      "build": { "mode": "primary" }
    }
  }
  ```

- **Agent Markdown**：在 `.opencode/agents/<name>.md` 的 **frontmatter** 里写 `mode: subagent`（或 `primary` / `all`），会通过 `md.data` 被解析进 config，再在 agent 合并时覆盖默认值（`item.mode = value.mode ?? item.mode`）。

使用界面中没有「agent 的 mode」配置项，只能通过上述文件修改。

---

### 2.3 command.subtask === true

#### 内置命令（代码写死）

在 `command/index.ts` 里：

- **init**：未设置 `subtask`，即不强制以子任务方式执行。
- **review**：显式写死 `subtask: true`。

因此 **review 命令默认就会以子任务方式执行**，同样无需在界面配置。

#### 用户自定义命令（仅配置，无 UI）

- **JSON 配置**：在 `opencode.json` 的 `command` 段里为某个命令设置 `subtask: true` 或 `subtask: false`（config 中 Command 的 schema 包含 `subtask: z.boolean().optional()`）。
- **命令 Markdown**：在 `.opencode/command/<name>.md` 或 `.opencode/commands/<name>.md` 的 **frontmatter** 里写 `subtask: true`，会通过 `md.data` 被解析进 config。

例如 `.opencode/command/commit.md` 中可写：

```yaml
---
subtask: true
---
```

使用界面中没有「命令的 subtask」配置项，只能通过上述文件修改。

---

### 2.4 判定逻辑（何时走子任务）

在 `session/prompt.ts` 的 `executeCommand` 中：

```ts
const isSubtask =
  (agent.mode === "subagent" && command.subtask !== false) || command.subtask === true
```

含义：

- 若**命令**显式设置 `subtask: true`，则一定走子任务。
- 若**命令**未设置或为 `false`，但该命令绑定的 **agent** 的 `mode === "subagent"`，则仍走子任务（除非命令显式 `subtask: false`）。

因此：既可以通过「命令的 subtask」控制，也可以通过「agent 的 mode」间接控制；两者都**只能通过配置文件或 .opencode 下的 Markdown 配置**，界面上没有对应开关。
