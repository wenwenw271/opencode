# opencode 工具执行完整流程

本文描述从「用户发消息」到「模型调工具、执行、结果落库」的完整链路。分两条路径：**LLM 调用的工具**（如 read、bash、task）与 **subtask/compaction 等“内部任务”**。

---

## 一、整体入口：loop 与工具解析

- **入口**：`session/prompt.ts` 的 `loop()`（在 `prompt()` 里被调用）。
- 每轮循环会：
  1. 从会话消息里找 `lastUser` / `lastAssistant` / `lastFinished`，并收集 `tasks`（只含 `type === "compaction"` 或 `"subtask"` 的 part）。
  2. 若有 **subtask**：直接走「子任务执行」分支（见第二节）。
  3. 若有 **compaction**：走压缩分支（`SessionCompaction.process`），不涉及普通工具。
  4. **正常分支**：取 agent、插入提醒、**创建 SessionProcessor**、**解析工具**、调 LLM。

工具解析与 LLM 调用的关系：

```
loop()
  → resolveTools({ agent, session, model, processor, ... })   // 得到「带包装 execute 的」tools
  → processor.process({ user: lastUser, messages, tools, model, ... })
       → LLM.stream(streamInput)   // streamInput 里已包含上述 tools
       → AI SDK streamText({ tools, messages, ... })
```

也就是说：**真正执行工具的是 AI SDK**；opencode 只负责「注册工具列表 + 包装每个工具的 execute」，并在流式事件里把「工具调用 / 结果」写回 Session。

---

## 二、两条“执行工具”的路径

### 路径 A：subtask（不经过 LLM，直接执行 TaskTool）

- **触发条件**：本轮从消息里收集到的 `tasks` 中，`task?.type === "subtask"`（由 `SessionPrompt.command()` 写入的 part）。
- **位置**：`session/prompt.ts` 约 390–565 行。

流程简述：

1. `tasks.pop()` 得到一个 subtask part（含 `prompt`、`description`、`agent`、`command` 等）。
2. 用 `TaskTool.init()` 得到 `taskTool`。
3. 为这条「子任务」创建一条助手消息和一个 `type: "tool"` 的 part（tool 名为 `TaskTool.id`），状态先设为 `running`。
4. 构造 `Tool.Context`（`taskCtx`），其中 `metadata()` 会 `Session.updatePart` 更新该 part。
5. 触发插件 `tool.execute.before`（tool: `"task"`）。
6. **执行**：`taskTool.execute(taskArgs, taskCtx)`；内部会再调 `SessionPrompt.prompt()` 开子会话跑子 agent。
7. 触发插件 `tool.execute.after`。
8. 根据结果 `Session.updatePart` 把该 part 置为 `completed`（含 output/title/metadata/attachments）或 `error`。
9. 若 `task.command` 存在，会插入一条合成用户消息（例如 “Summarize the task tool output above…”），以便下一轮 loop 继续。

**要点**：subtask 不经过 LLM 的 tool-call，是 loop 根据消息里的 subtask part **直接**调 `TaskTool.execute`，因此这条路径不经过「模型返回 tool_calls → SDK 执行工具」的流程。

---

### 路径 B：LLM 调用的工具（read、bash、task、MCP 等）

这条路径是「模型在回复里发出 tool_calls → AI SDK 调用工具的 execute → 结果写回消息」。

#### 1. 工具列表从哪来

- **来源**：`session/prompt.ts` 的 `resolveTools()`（约 776–968 行）。
- **步骤**：
  - 调用 `ToolRegistry.tools(model, agent)` 拿到当前 agent 可用的内置工具（如 ReadTool、BashTool、TaskTool、EditTool、WriteTool 等）；`ToolRegistry` 在 `tool/registry.ts` 里用 `all()` 拉取列表，再按 model/agent 做过滤。
  - 对每个工具调用 `item.init({ agent })` 得到 `description`、`parameters`、`execute`。
  - 用 `ProviderTransform.schema(model, z.toJSONSchema(item.parameters))` 转成当前模型可用的 JSON Schema。
  - 用 AI SDK 的 `tool()` 包一层：`tools[item.id] = tool({ id, description, inputSchema, async execute(args, options) { ... } })`。
  - 在包装的 `execute` 里：
    - 用 `context(args, options)` 得到 `Tool.Context`（sessionID、messageID、callID、abort、agent、messages、`metadata()`、`ask()`）。
    - `metadata()` 内部通过 `processor.partFromToolCall(options.toolCallId)` 找到对应 ToolPart，并 `Session.updatePart` 更新 title/metadata/status 等。
    - 触发 `tool.execute.before` → **`item.execute(args, ctx)`**（真实工具逻辑）→ 触发 `tool.execute.after`，最后把 `result`（含 output、title、metadata、attachments）返回给 AI SDK。
  - 再合并 `MCP.tools()` 返回的 MCP 工具，同样包一层 execute（内含权限 `ask`、结果转 text/attachments、truncate 等）。

因此：**所有给 LLM 的工具**都是「ToolRegistry / MCP 的实例 + 同一套包装（context、插件、Session 更新）」；**真正干活的**是各 `Tool.Info` 的 `execute(args, ctx)`（如 `ReadTool`、`BashTool`、`TaskTool` 等）。

#### 2. LLM 流与工具调用的驱动

- **驱动**：`session/processor.ts` 的 `process(streamInput)`。
- **步骤**：
  - 在 `while (true)` 里调用 `LLM.stream(streamInput)`，得到 `stream`。
  - `for await (const value of stream.fullStream)` 消费 AI SDK 的 fullStream 事件。
  - **工具相关事件**：
    - **`tool-input-start`**：为该次调用创建一条 `type: "tool"` 的 part（`Session.updatePart`），并把 `value.id` 作为 callID 记入 `toolcalls[value.id]`，状态 `pending`。
    - **`tool-call`**：模型已给出工具名和参数；用 `Session.updatePart` 把对应 part 更新为 `status: "running"`、写入 `value.toolName`、`value.input`；同时做 doom_loop 检测（同工具同参数连续 N 次则触发权限询问）。
    - **`tool-result`**：AI SDK 已执行完该工具的 `execute` 并拿到返回值；用 `Session.updatePart` 把 part 置为 `status: "completed"`，写入 output、metadata、title、attachments、time.end。
    - **`tool-error`**：执行失败；把 part 置为 `status: "error"`，写入 error；若是权限/Question 拒绝且未开 continue_loop_on_deny 则设 `blocked = true`。

也就是说：**工具的真实执行发生在 AI SDK 内部**（streamText 收到 model 的 tool_calls 后，会去调我们传入的 `tools[id].execute(args, options)`）；我们的包装 `execute` 里调了 `item.execute(args, ctx)`，所以 **Tool 的 `execute` 在「tool-call 事件之后、tool-result 事件之前」被调用**。processor 的循环只是在**消费流事件**，把「调用中 / 结果」同步到 Session 的 part 上。

#### 3. LLM.stream 与 AI SDK 的衔接

- **位置**：`session/llm.ts` 的 `stream()`。
- **步骤**：
  - 用 `resolveTools(input)` 仅做「按权限/用户设置禁用部分工具」的过滤，不改变工具实现。
  - 调用 `streamText({ tools, messages, model, toolChoice, ... })`（AI SDK）。
  - 模型返回的 tool_calls 会由 SDK 解析并依次调用 `tools[toolName].execute(args, options)`；我们的 `execute` 里已经包含「context → plugin before → item.execute → plugin after → return」，因此 **一次工具调用 = 一次我们包装的 execute = 一次真实 Tool 的 execute + Session 更新（通过 metadata/partFromToolCall）+ 插件**。
  - 流里随后会出现 `tool-result` / `tool-error`，processor 用它们把 part 写成 completed/error。

#### 4. 单工具执行链（Tool 侧）

以「模型调 read 工具」为例，从定义到执行的层次：

1. **定义**：`tool/read.ts` 等里用 `Tool.define("read", { init, parameters, execute })` 注册；`Tool.define` 会在 `execute` 外包一层「参数 Zod 校验 + 输出 truncate」。
2. **注册**：`tool/registry.ts` 的 `all()` 包含 `ReadTool`；`ToolRegistry.tools(model, agent)` 过滤后返回包含 ReadTool 的列表。
3. **解析**：`prompt.ts` 的 `resolveTools()` 对每个 item 做 `tool({ id, description, inputSchema, execute: async (args, options) => { ... item.execute(args, ctx) ... } })`，并注入 `context`（含 partFromToolCall、metadata、ask）。
4. **调用**：模型在回复里带 `tool_calls: [{ name: "read", arguments: { filePath: "..." } }]`；AI SDK 调用 `tools["read"].execute(args, options)`。
5. **执行**：包装的 execute 里 `item.execute(args, ctx)` 实际跑到 `ReadTool` 的 execute，读文件、返回 `{ title, metadata, output, attachments? }`；若工具内部调了 `ctx.metadata()`，会更新当前 ToolPart 的 title/metadata。
6. **落库**：同一轮流里，processor 收到 `tool-result`，用 `Session.updatePart` 把该 part 写成 completed，带上 output、metadata、title、attachments。

## 三、关键文件与职责小结

| 环节           | 文件 / 命名空间           | 职责 |
|----------------|---------------------------|------|
| 工具定义       | `tool/tool.ts` (Tool.define) | 参数校验、输出截断包装 |
| 工具列表       | `tool/registry.ts` (ToolRegistry) | all()、tools(model, agent)、过滤、插件/自定义工具 |
| 解析并包装执行 | `session/prompt.ts` (resolveTools) | ToolRegistry + MCP → 包装 execute、context、plugin、Session 更新 |
| 流与 part 更新 | `session/processor.ts` (SessionProcessor) | fullStream 事件：tool-input-start / tool-call / tool-result / tool-error → Session.updatePart |
| 调用模型与工具 | `session/llm.ts` (LLM.stream) | streamText(tools, messages, ...)；工具由 AI SDK 按 model 的 tool_calls 调用 |
| 子任务执行     | `session/prompt.ts` (loop 内 task?.type === "subtask") | 直接 TaskTool.execute，不经过 LLM tool-call |
| 单工具实现     | `tool/read.ts`、`tool/bash.ts`、`tool/task.ts` 等 | 实现 `execute(args, ctx)`，可调 ctx.metadata() / ctx.ask() |

## 四、流程简图（LLM 工具路径）

```
用户消息 → prompt() → loop()
  → 本轮回退找 lastUser / lastFinished，收集 tasks
  → 无 subtask/compaction 时：
       resolveTools() → ToolRegistry.tools() + MCP.tools()
         → 每个工具：tool({ id, description, inputSchema, execute: 包装 })
       SessionProcessor.create(assistantMessage)
       processor.process({ tools, messages, model, ... })
         → LLM.stream(streamInput)
              → streamText({ tools, messages, ... })  // AI SDK
         → for await (fullStream):
              tool-input-start  → Session.updatePart(tool part, pending)
              tool-call         → Session.updatePart(running, input)
              [AI SDK 内部调用 tools[name].execute(args) ]
                → 我们的 execute: context → plugin before → item.execute(args, ctx) → plugin after → return
              tool-result       → Session.updatePart(completed, output, ...)
              或 tool-error     → Session.updatePart(error, ...)
         → 若 finishReason 为 tool-calls，下一轮 while 再 LLM.stream(更新后的 messages)
  → 直到 finish 为 stop / 出错 / 需要 compact
```

subtask 路径不经过「resolveTools → process → fullStream」，而是 loop 内直接 `TaskTool.execute(taskArgs, taskCtx)`，并在内部再调 `SessionPrompt.prompt()` 完成子会话。

## 五、loop 为什么能一直循环？任务何时算结束？

### 5.1 循环为什么能持续

每一轮 `while (true)` 都会：

1. **重新拉消息**：`msgs = await MessageV2.filterCompacted(MessageV2.stream(sessionID))`，得到当前会话的「有效窗口」消息。
2. **从后往前扫**：得到本轮的 `lastUser`、`lastAssistant`、`lastFinished`，以及未处理的 `tasks`（compaction/subtask parts）。
3. **三种分支**：
   - 若有 **subtask**：执行 `TaskTool.execute`，写 part，然后 **continue**（下一轮再拉消息、可能还有新 task 或继续走 LLM）。
   - 若有 **compaction**：执行 `SessionCompaction.process`，可能 **break** 或 **continue**。
   - **正常分支**：调 `processor.process()`（内部 `LLM.stream` → 模型可能返回文本或 tool_calls → SDK 执行工具 → 流结束）。`process` 返回后：
     - 若返回 **`"stop"`** → **break**，loop 结束。
     - 若返回 **`"compact"`** → 创建压缩任务，**continue**。
     - 否则返回 **`"continue"`** → **continue**，下一轮再拉消息、再调 LLM。

所以「能不断循环」的原因有两个：

- **还有待办**：`tasks` 里还有 compaction/subtask，或上一轮 LLM 返回了 **tool-calls**（模型要调工具），SDK 已执行完工具并把「助手消息 + tool_calls + tool 结果」写回会话；下一轮拉到的 `lastAssistant` 的 `finish` 仍是 `"tool-calls"`，不满足「任务结束」条件，于是再走正常分支，用**包含 tool 结果的新消息列表**再调一次 LLM，让模型「接着上次工具结果」继续回复。
- **状态在消息里**：是否结束不看内存里的局部变量，而看**当前会话里最后几条消息**：最后一条助手消息的 `finish` 是什么、是否在最后一条用户消息之后。

### 5.2 任务何时算结束（loop 何时 break）

代码里**真正结束 loop** 的出口如下（均在 `session/prompt.ts` 的 `loop()` 内）：

| 出口 | 条件 | 含义 |
|------|------|------|
| **abort** | `abort.aborted` | 外部取消（如用户停止）。 |
| **本轮已有一轮完整回复** | `lastAssistant?.finish` 存在且 **不在** `["tool-calls", "unknown"]` 里，且 `lastUser.id < lastAssistant.id` | 当前「最后一条助手消息」已经是对「最后一条用户消息」的**收尾回复**（例如 `finish === "stop"` / `"length"` / `"content_filter"` 等），即模型已经说完、不再要工具。 |
| **结构化输出** | 使用了 `format.type === "json_schema"` 且拿到了 `structuredOutput` | 已拿到结构化结果，直接结束。 |
| **结构化输出失败** | `format.type === "json_schema"` 且模型没产出结构化输出 | 记错并结束。 |
| **process 返回 stop** | `processor.process()` 返回 `"stop"` | 权限/Question 拒绝导致 blocked，或发生未重试错误。 |

其中**最核心的「任务结束」判断**是第二条：

```ts
// 已有助手回复且非 tool-calls/unknown，且在该用户消息之后，则本轮不再生成，退出
if (
  lastAssistant?.finish &&
  !["tool-calls", "unknown"].includes(lastAssistant.finish) &&
  lastUser.id < lastAssistant.id
) {
  log.info("exiting loop", { sessionID })
  break
}
```

含义：

- **`lastAssistant.finish` 存在**：这条助手消息已经有一个「结束原因」。
- **不是 `tool-calls` / `unknown`**：模型不是「只发了 tool_calls」或未知状态，而是**正常结束**（如 `stop`、`length`、`content_filter` 等）。
- **`lastUser.id < lastAssistant.id`**：这条助手消息是在「当前最后一条用户消息」之后产生的，即是对用户最后一问的回复。

满足这三条时，认为「当前用户问的这一轮」已经有一轮完整回复，任务结束，loop 退出。

### 5.3 和「工具调用」的关系

- 当模型**返回 tool_calls** 时，SDK 执行工具并把结果写回；助手消息的 `finish` 会被设为 **`"tool-calls"`**（见 `processor.ts` 里 `finish-step` 的 `value.finishReason`，以及 subtask 分支里显式写的 `assistantMessage.finish = "tool-calls"`）。
- 此时 `["tool-calls", "unknown"].includes(lastAssistant.finish)` 为 true，上面的退出条件**不成立**，loop 会 **continue**。
- 下一轮重新拉消息，消息里已经包含「助手 + tool_calls + tool 结果」；再调 LLM 时，模型会看到这些结果并继续生成；若这次模型**不再发 tool_calls** 而是正常结束，`finish` 会变成 `"stop"` 等，下一轮循环就会命中退出条件，**任务结束**。

此外，agent 可配置 `steps`（默认无穷）。当 `step >= maxSteps` 时会在发给模型的消息里插入 `MAX_STEPS` 提示，**建议**模型在本步收尾；真正结束仍依赖模型返回非 tool-calls 的 finish，进而满足上面的退出条件。
